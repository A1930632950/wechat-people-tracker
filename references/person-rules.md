# 人物识别与防误合并规则

## 一、人物 ID 与索引

- 每个确认的人物一个 ID：`P0001` 起递增，永不复用。
- `data/index.md` 维护总索引：ID、姓名、微信昵称、曾用昵称、备注关系、档案文件名。
- 人物档案命名：`data/people/P0001-姓名.md`。改名/换昵称只更新 index 与档案头部，**文件名与 ID 不变**。

## 二、人物档案头部字段

```markdown
- 人物ID: P0001
- 姓名: 陈XX（未知则空）
- 微信昵称: 哈哈哈
- 曾用昵称: 陈老师（每次变更追加，不删除旧的）
- 关系备注: 大学同学
- 其他识别信息: 在上海工作、有个妹妹
- 建档: B0001 ｜ 2026-10-04
```

## 三、匹配流程（每次更新）

1. 用户提供了人物ID → 直接定位。
2. 只提供了昵称/姓名 → 在 `index.md` 中精确匹配（昵称或曾用昵称字段）。
3. 精确匹配失败 → 检索"其他识别信息"做**弱匹配**：
   - 弱匹配命中 → **不得自动合并**。输出提示："疑似与 P000X 陈XX（大学同学）为同一人，依据：XXX。是否合并？"等用户确认。
   - 弱匹配无命中 → 新建人物，分配新 ID。
4. 同一昵称对应多个已有人物（两个"小陈"）→ 全部列出候选让用户选择，**禁止默认选第一个**。

## 四、硬规则

- **"我"（用户本人）不建档、不占 P 编号**：用户是系统中心节点。每次上传的视角指定（谁是我）见 SKILL.md"输入要求"；事件归属按发言人裁定，我方发言仅在影响对方事项时写入对方档案备注/待跟进。
- **模糊信息永不自动合并两个人物。** 宁可多建一个档案之后手动合并，不可错并。
- 用户确认合并时：保留建档更早的 ID，另一档案的事件全部迁入，其 ID 在 index 中标注"已并入 P000X"留痕。
- 对话中出现的新人物（"我最近认识了个人叫老王"）→ 若此人自身产生事件（如将一起做事），可为其建档并在事件中体现；若只是被提及，不建档，只在提及者的相关事件备注中出现。
