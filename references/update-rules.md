# 增量更新规则（去重、状态迁移、溯源）

## 一、批次（Batch）与溯源

- 每次用户上传 = 一个批次，编号 `B0001` 起递增，永不复用。
- 原始粘贴文本全量存入 `sources/BXXXX.md`，头部写入：锚点日期、聊天对象（人物ID）、用户/对方标记方式。
- 每条事件的"来源"字段格式：`BXXXX｜原文摘录（≤30字）`。日后 AI 记错时可按批次号回溯原文核对。

## 二、事件 ID

- 每条事件编号 `E0001` 起递增（全局唯一，记在各人物档案内），永不复用、永不重排。
- 删除或合并事件时在备注中记录"由 E000X 合并/取代"，保持可追溯。

## 三、新事件 / 补充 / 状态变化 / 重复 的判定

新聊天提取出候选事件后，与该人物已有事件按顺序比对：

1. **同日期（或时间区间重叠）+ 同类型 + 同主题** → 判定为同源事件，走"补充"或"状态变化"。
2. **日期邻近（±7 天）+ 同类型 + 同主题**（如"准备去上海出差"与"已经到上海了"）→ 判定为同一事件的进展，走"状态变化"，在原事件追加状态行。
3. 以上都不满足 → 新事件。

边界情况优先归为"补充"而非新增；拿不准时在更新摘要中列为**存疑项**交用户裁决。

## 四、状态迁移表

事件状态只有六个值：`计划中 → 进行中 → 已完成`，以及 `已取消`、`已改变`、`搁置`。

合法迁移：

```
计划中 → 进行中 → 已完成
计划中 → 已取消
计划中 → 已改变（新计划另立新事件，原事件标"已改变"并在备注指向新事件ID）
进行中 → 已完成 / 已取消 / 搁置
搁置 → 进行中（恢复）
```

- 每次状态变化在事件的"状态历史"中**追加一行**（日期 + 新状态 + 批次号），不覆盖旧状态 → 满足"历史保留，当前状态更新"。
- 事件的"状态"字段始终显示**最新状态**。

## 五、覆盖 / 补充 / 保留的裁定

- **事实类信息变化**（换了工作、搬家）：旧事件保留并已终结，新增事件，当前状态以新事件为准。
- **补充**：新信息丰富旧事件细节（如补充出差同行人）→ 写入旧事件备注，不新增。
- **矛盾信息**（先说 10 月去北京，后说去成都）：不擅自删除，两批次都记录，状态标"已改变"，备注写明矛盾点；重大矛盾列入存疑项。

## 六、更新前备份（硬性步骤，先备份后写入）

- **时机**：每次"更新"在写入任何档案文件**之前**执行，无论改动大小。
- **范围**：本次将被修改的文件——至少包括 `index.md`、相关 `people/PXXXX-*.md`、`followups.md`。原始聊天文本（`sources/`）只增不改，无需备份。
- **位置与命名**：`data/backup/BXXXX-<YYYYMMDD-HHMM>/`，批次号对齐本次更新批次，目录内保持与 `data/` 相同的相对路径（如 `backup/B0007-20261004-2350/people/P0001-张三.md`）。
- **方式**：完整文件复制（cp），不做裁剪或改写；备份必须先于写入完成并确认成功，备份失败则中止本次更新并告知用户。
- **摘要标注**：更新摘要末尾注明 `备份：data/backup/BXXXX-…/（共 N 个文件）`。
- **保留策略**：默认全部保留（均为小体积 Markdown）；仅当用户明确要求清理时才删除旧备份，且每次只删用户确认的批次。
- **恢复**：更新结果有误时，将对应备份目录内的文件复制回 `data/` 原路径即可回滚；回滚后按正常流程重新更新。

## 七、本次更新摘要（每次"更新"必输出）

```
【本次更新摘要】批次 BXXXX ｜ 锚点日期 ｜ 人物
- 新增事件 N 条：E00XX …
- 状态变化 M 条：E00XX 计划中→进行中 …
- 补充 K 条：E00XX …
- 过滤丢弃：约 X 条闲聊/低价值信息
- 存疑 J 条：（原文引用 + 疑点 + 建议裁定）
```
